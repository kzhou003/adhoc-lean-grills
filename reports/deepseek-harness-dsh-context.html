01 / EXECUTIVE SUMMARY

先说结论

核心判断：DeepSeek Harness 提供 Agent 执行、会话事件、插件生命周期和扩展接口；dsh-context 是构建在这些接口上的上下文可观测与管理插件。它把 Harness 已经产生的会话事实转成可查询的投影、时间线、成本/活动信息和 Fleet 视图。它不是另一个 Agent runtime，也不是多 Agent 调度器。

DeepSeek Harness

负责“Agent 如何运行”：启动配置、Profile/Bundle 装配、Cordis 服务注入、插件激活与释放、Session Event、持久化和投影服务。

理解重点：生命周期与运行时契约，而不是某个 UI 页面。

dsh-context

负责“运行过程如何被看见”：Host 侧从事件折叠上下文状态并提供 API；Client 侧注册 Context、Fleet、Insights、命令与详情 UI。

理解重点：数据投影、缓存/冷读、Host-Client 分层与可观测性。

最重要的架构边界是：Fleet 展示 Agent 之间的委派、消息与成员关系，但真正的委派执行、Agent 生命周期和状态推进仍属于 Harness / Agent 运行时。不要把“能观察 Fleet”误解为“负责编排 Fleet”。

03 / RUNTIME ARCHITECTURE

Harness：插件化 Agent Runtime

3.1 分层理解

启动与配置

CLI / App Boot 负责读取 Profile、Bundle 与配置，解析依赖，装载插件树，并在生命周期收敛后判断必需插件是否成功激活。

Cordis 容器

插件通过 inject 声明依赖服务，通过 apply(ctx, config) 建立服务、事件监听和 slots。Fiber/effect 管理注册与释放。

Session 基础设施

Session 与 SessionEvent 提供会话身份、事件日志和可恢复的状态来源。事件日志可供 live drive、cold read 与恢复路径重放。

客户端承载层

Host 通过 API/推送帧提供数据；Client 通过 slots、store 和 UI 组件把能力放入对话、侧栏、设置页等位置。

3.2 插件生命周期心智模型

Profile / Bundle config
        │
        ▼
Loader resolves packages + dependencies
        │
        ▼
Cordis plugin tree mounts
        │
        ├── inject required services
        ├── apply(ctx, config)
        ├── register services / routes / slots
        └── own effects and disposers
        │
        ▼
Runtime active ── config reload / HMR ──► reconcile
        │
        ▼
fiber disposal releases registrations and listeners

关键不是“插件导出一个 apply 函数”这么简单，而是注册行为与 fiber 生命周期绑定。插件停用时应释放监听、路由、slot、定时任务和缓存资源；如果把资源注册到不受控的全局对象，热更新或卸载时就容易出现重复订阅、悬挂引用和状态泄漏。

3.3 为什么 Cordis 注入重要

  • 依赖显式化：插件声明依赖的服务名，运行时负责等待提供者；插件不需要自己到处查找全局单例。
  • 生命周期可组合：effect 的 disposer 与 fiber 释放绑定，资源归属更清楚。
  • 能力边界：插件只需要依赖稳定的服务接口，不必侵入 Agent loop 或 Session 内部实现。
  • 可热更新：Loader 可以在配置变化后协调插件实例和依赖关系，但失败策略取决于必需/可选条目及其依赖。
04 / SESSION PROJECTION

Session Projection：把事件日志变成读模型

这是 Harness 与 dsh-context 之间最关键的架构契约。Harness 的 SessionProjectionRegistry 统一订阅 session/event，驱动各领域注册的 projection unit。领域插件只定义状态如何从事件演进，不自行订阅事件流。

4.1 一个 projection unit 的形状

ProjectionDefinition<Key, State> = {
  key,
  stateSchema,
  init(header, inheritedEventCount),
  apply(previousState, committedEvent),
  wire?: {
    viewSchema,
    view(state),
    summary?
  },
  stateVersion
}
  • init 定义空日志起点；apply 是同步、确定性的状态转移函数。
  • 如果某事件与该 unit 无关，apply 应返回原 state 引用。运行时用引用变化判断是否需要下游计算。
  • wire.view 把 Host 内部状态映射成客户端可见值；Host-only unit 不需要 wire。
  • stateVersion 用于持久化缓存兼容性；改变状态字段或折叠语义时必须谨慎升级。

4.2 为什么要同步 fold

投影的状态转移必须同步完成，避免不同 carrier 读取到不一致的事件切面。一个 Session 的 snapshot 带有共享水位 asOfSeq，它表示所有返回值都反映到同一个最后事件序号。客户端接收的是完成的读模型，而不是各自消费领域事件后自行推导。

SessionEvent已提交事件
→
Registry统一驱动
→
apply()纯状态折叠
→
view()读模型
→
CarrierAPI / push

4.3 Projection Cache 与恢复

持久化 cache 保存每个 session/key 的版本、序号和状态值。冷读可以用匹配版本的 checkpoint 作为起点，再从日志读取 suffix 并继续 fold；版本不匹配、日志截断或 checkpoint 水位超出真实日志时，必须丢弃缓存并从完整日志重建，不能把过期缓存误当成当前状态。

读取路径行为适用场景
Cached view直接查看已持久化且版本匹配的 projection row，不读日志；可能陈旧但不应错误归属。列表页快速展示
Live snapshot从 live watermark cells 同步读取所需 key，返回一致的 asOfSeq。打开中的 Session
Cold snapshot / restorecheckpoint seed + 日志 suffix replay；检测日志缩短，必要时全量重读。已关闭或恢复中的 Session
性能细节：Registry 对一个 committed event 先驱动所有 unit，再以 Object.is 比较 view 结果。未改变的 view 不发布；event-level feed 可以把同一事件导致变化的多个 key 合并通知。这个设计减少无意义的 UI 更新，也让多个投影共享同一事件水位。

4.4 Summary 与 Full Snapshot

列表行只携带 summary key 集合；打开 Session、follow baseline 或 control baseline 可以携带完整 projection。通过类型标记与 wire.summary 协调排除大字段，避免把 timeline 明细、重型记录或非必要状态塞进每一个列表行。

05 / DSH-CONTEXT IMPLEMENTATION

dsh-context：Host 与 Client 两侧的插件

5.1 包与入口

package.json 的主入口是编译后的 lib/index.js，客户端另导出 ./client。源码分为 src/host、src/client、src/shared 等边界。插件 manifest 声明 client injection 包和 web platform；Host 入口依赖 sessionProjections。

5.2 Host 入口：注册投影与路由

export const name = 'dsh-context'
export const inject = ['sessionProjections']

export function apply(ctx, config) {
  const coldReads = makeColdReadGate()
  const catalog = createCatalogService()
  const pricing = createCostSource(catalog)

  watchFleetChannel(ctx, coldReads)
  watchAttachmentChannel(ctx, coldReads)

  // 低于 baseline 时注册 fallback projection
  // 否则启用完整的 timeline / headers / activity
  // 并挂载 detail / delta / facts / overview 等通道
}

源码中的 Host apply() 先准备 cold-read gate、catalog 和 pricing source，再安装 version、balance、recommendation、skill、fleet、attachment 等通道。满足 Harness baseline 后创建 tool attribution、step identity、detail gate、shadow state；注册 timeline、headers、activity projection；随后安装 sweep、backfill、snapshot、overview 与 prompt injection。

Timeline

把 Session 事件与工具/请求相关事实折叠为可查询的上下文时间线，供概览与详情使用。

Headers

维护头部信息和工具归属等索引，让界面能解释某条活动由哪个工具/Agent 产生。

Activity

把活动状态整理成按时间/会话维度可浏览的聚合读模型。

Cold-read gate

控制昂贵的历史明细读取，避免多个 UI 视图同时触发重复的日志折叠工作。

5.3 Client 入口：把能力挂到产品界面

Client apply(ctx) 注册字典、初始化 view kit 和 settings，建立 ContextView 与 FleetView；然后通过 slots.inject/register 将 UI 插入 conversation view、sidebar、assistant actions、input overlay、plugin config 和 insight page。另注册 context command。

  • Context View：当前会话的上下文结构、事件与详情入口。
  • Fleet View：围绕 Agent 团队成员、委派、消息和状态的观察视图。
  • Context command / modal：从命令或输入区域快速打开上下文浏览能力。
  • Insight page：跨会话的概览与活动信息。
  • Settings：通过 config forms 将 placement 和配置暴露给用户。

Client 还在 effect cleanup 中 reset warm-up、timeline detail、attachment paths、version source、cost refresh 和 retention，说明缓存与监听是有明确释放路径的，而不是永久全局状态。

5.4 一个重要的分层事实

Host 负责权威数据、事件折叠、冷读、成本归因与 API；Client 负责呈现、交互、局部状态与 UI slot 生命周期。两边共享类型和协议，但 Client 不应该复制 Host 的事件折叠逻辑。这个分层能让数据模型更一致，也减少前端依赖运行时内部实现的程度。

06 / END-TO-END DATA FLOW

Fleet：从委派事实到可观察视图

从 src/host/fleet.ts 可见，插件定义了 /api/dsh-context/fleet 路由，并为 detail mode 区分 preview、history、full。代码会提取结构化 descriptor、消息正文，并对消息数量和文本长度做上限控制（例如消息数上限 80、单条消息文本上限 400 字符、batch 上限 16）。这些约束表明它更像有界的诊断/展示 API，而不是无限制导出完整 Agent transcript。

→

→

Fleet 数据处理值得注意的地方

  • descriptor 只接受已知 mode（one-shot / continuable），并挑选白名单字段。
  • 从内容块抽取文本时只拼接 text block；会剥离特定 system-reminder 前缀。
  • 对 message、prompt、reply 等文本做截断，限制 payload 规模。
  • 通过 preview/history/full 控制读取深度；冷读 gate 与 fold cache 协助避免不必要的全量日志读取。
  • Fleet API 是观察面：它整理已有执行事实，但不等于创建子 Agent、决定任务分配或驱动下一轮执行。
不要混淆三个概念：Agent orchestration（谁启动谁、任务如何分配、何时重试）属于执行/编排层；Fleet telemetry（谁参与、发了什么消息、当前进展）属于观测层；Context projection（如何从事件恢复可读状态）属于数据模型层。dsh-context 主要实现后两者。
07 / DESIGN REVIEW

设计优势、代价与风险

设计收益代价 / 风险
Event log + deterministic projection状态可重建、可审计；领域状态逻辑集中。projection 语义升级、历史事件兼容与全量 replay 成本高。
Shared registry drive避免每个插件各自订阅；所有 projection 共享事件切面。单个慢/异常 unit 可能影响事件处理路径；必须保证 apply 同步、轻量、无副作用。
Checkpoint + suffix replay降低冷读开销；版本水位可校验。cache identity、log truncation、stateVersion 演进需要严谨测试。
Host / Client separation前端消费稳定 read model，避免重演领域事件。协议、schema、compatibility baseline 要持续维护。
Bounded Fleet detail API限制响应体与历史读取成本。截断内容会损失上下文；preview/history/full 的语义需清晰。
Cordis plugin lifecycle模块化、可注入、可释放，支持动态配置。依赖图和注册顺序更复杂；漏掉 disposer 会造成热更新问题。

我会重点审查的工程风险

  • Projection replay determinism：相同事件序列与 header 是否必定得到相同状态？对 fork inherited prefix、format migration 是否有测试？
  • State version discipline：字段变化是否升级 version？旧 checkpoint 是否安全失效？有没有 suffix replay 等价性测试？
  • Event hot path budget：每个 unit 的 apply 是否保持 O(1) 或有界增量？是否会在同步 listener 中做 I/O？
  • Cold-read deduplication：并发打开相同 session 时是否共享读取任务？取消一个 consumer 会不会错误取消其他 consumer 的工作？
  • Payload/privacy boundaries：prompt、tool output、agent message 的展示是否有长度、权限和敏感字段策略？
  • Compatibility matrix：不同 Harness release 的 fallback projection、API route 和 client injection 是否有真实集成测试。
