Omarchy 4.0：从源码看懂这个系统，再把它用好

Omarchy 是 DHH 做的一套 Arch Linux + Hyprland 发行版层，4.0（quattro 分支）把它改成了 pacman 包发布、Lua 写的 Hyprland 配置和一个常驻的 Quickshell 桌面。这份导读分两半：前半从源码讲它怎么装、命令怎么路由、配置怎么分层、主题怎么一键换遍全系统、更新和迁移怎么跑、“agentic”具体指什么；后半是面向日常使用的功能指南：快捷键体系、菜单、剪贴板、听写、截屏录屏、AI 工具链、Web App、自定义与维护，以及哪些操作会覆盖你的配置。所有源码链接固定在同一个 commit，构建时逐条校验。

类比 · 一家定好菜单的餐馆

Omarchy 自称 omakase：厨师替你点好菜。/usr/share/omarchy 是后厨——菜谱和原料归厨房，每次进货（更新）都会整箱替换；~/.config 是你的餐桌——端上来以后怎么调味是你的事，厨房不会再碰；~/.local/state/omarchy 是传菜口——当前这一桌的配色、开关状态都在这里临时放着，由厨房生成，你不该伸手进去。看懂这三块地方各归谁，就看懂了 Omarchy 的大半设计。

2. 打包与安装

2.1 职责与难点

职责：把仓库里的东西放到目标机器的正确位置，并为每个用户准备好家目录。难点：有些文件必须在 useradd -m 之前就位（/etc/skel、limine、snapper 配置），有些只能在用户第一次图形登录时做（启用 user units、音频调校）；还要支持“给别人装机、首次开机再建用户”的预装镜像。

2.2 两个包

v4 从同一个仓库构建两个 Arch 包，PKGBUILD 在外部的 omarchy-pkgs 仓库（file-layout.md）：

包 内容 安装到
omarchy bin/、install/、migrations/、themes/、shell/ /usr/bin/omarchy-*、/usr/share/omarchy/
omarchy-settings /etc/skel/**（来自 config/）、/etc drop-in、字体、plymouth/sddm 主题、limine/snapper 配置 /etc/**、/usr/share/omarchy/default/ 等

OMARCHY_PATH 由 env-bootstrap 设置：有 /etc/omarchy.conf（dev-link 写入）就读它，否则强制为 /usr/share/omarchy。按 AGENTS.md 的规定，运行时代码只能依赖这个变量，不准自己推导回退路径。

2.3 三层家目录

2.4 安装流水线

本仓库没有 install.sh 这类入口，安装由外部 ISO 编排（install-scripts.md）。仓库提供的是目标机上的三个命令：

阶段 命令（身份） 做什么
系统级 omarchy-apply-system（root，在 chroot 里） 依次 source config/all.sh（主题系统、浏览器策略、锁定策略、ssh、docker、snapper、防火墙…）→ 硬件叶子 hardware/all.sh（按厂商分组约 79 项）→ 登录 → post-install
用户级 omarchy-provision-user（用户） 把 agent skill 软链进 6 种代理的目录（L87–101），source user/all.sh，默认主题设为 Tokyo Night（theme.sh）
首次登录 omarchy-provision-first-run 启用 user units、平台分派 setup-user、音频调校、欢迎页

每个叶子脚本都通过 run_logged 执行并写进 /var/log/omarchy-install.log。包清单按 base → 架构 → 平台拼接（omarchy-pkg-defaults）：base.packages 有 164 个包。

容易误解的地方：install/ 和 migrations/ 下的脚本没有 shebang，是被 source 的，不能直接执行（Style）。

3. CLI 路由器：omarchy <group> <cmd>

3.1 职责与难点

591 个命令要能用空格分词的方式调用（omarchy theme set），要能自省（给人看的帮助、给代理看的 JSON），而且快：快捷键、菜单、shell 都在频繁调用它。

3.2 原理：文件名就是路由

没有注册表：每个可执行的 bin/omarchy-* 就是一个命令，omarchy-theme-set 默认路由为 omarchy theme set（cli-router.md）。

3.3 契约：命令头部元数据

元数据写在文件开头的注释里，最多扫描 80 行（METADATA_SCAN_LIMIT），由 register_command 解析：

键 作用 例子
summary / args / examples 帮助文本，examples 用 | 分隔多个 theme-set
alias 额外的调用名 omarchy up、omarchy screenshot
group / name 覆盖默认路由 omarchy share
hidden=true 能调用但不列出（149 个命令） apply-system
requires-sudo=true 标记需要提权 omarchy-update

顶层分组列表的唯一来源是 GROUP_DESCRIPTIONS（73 组）。omarchy commands --json 输出全部命令的结构化记录，是代理发现能力的入口（自省与 --check）。

容易误解的地方：参数里只要出现 --help（-- 之后的除外）就只显示帮助、绝不执行（remaining_has_help_flag），所以给子命令传一个字面的 --help 需要放在 -- 后面。

4. Hyprland：Lua 配置与快捷键体系

4.1 职责与难点

Hyprland 新版本支持用 Lua 写配置。Omarchy 用它解决一个老问题：默认值要能随更新自动改进，而用户的修改又不能被覆盖。v3 时代默认值直接复制进用户文件，更新后要么覆盖、要么永远拿不到新默认；Lua 的 require 让默认值留在 /usr/share/omarchy，用户文件只写差异。

4.2 加载顺序

开关变量必须写在 require("default.hypr.omarchy") 之前：omarchy_default_bindings = false 关掉全部默认绑定，omarchy_preinstalled_bindings = false 只关预装应用和 Web App 的绑定，omarchy_default_gestures = false 关手势（hyprland.lua L6–14）。

4.3 快捷键的 DSL

所有默认绑定由 bindings.lua 从 default/hypr/bindings/ 加载八个文件（tiling、applications、utilities、clipboard、media、dictation、input-method、jis）。绑定函数在 helpers.lua：

写法 翻译成 位置
o.bind(keys, 描述, 动作) 注册绑定，描述会出现在 Super+K 速查里 L138
o.rebind(...) 先 unbind 再 bind L154
{ menu = "theme" } 打开某个菜单路由 L97–98
{ webapp = url, focus = true } 以 App 模式打开网页，已开则聚焦 L113–117
{ tui = "btop" } 在终端里启动一个 TUI L119–123

性能细节：如果动作登记在 default/omarchy/shortcuts 里，shell_dispatcher 会把它变成 Hyprland 全局快捷键，按键直接交给常驻的 shell 进程，不 fork 任何进程；不在表里的才回退成执行命令。

5. Quickshell 桌面与菜单

5.1 职责与难点

顶栏、菜单、通知、OSD、锁屏、剪贴板、emoji、dock、各种面板，在 v3 里是 waybar、mako、walker、hyprlock 等一堆独立程序；4.0 全部换成一个常驻的 Quickshell（QML）进程里的插件。难点是：它常驻、要省电，所以必须事件驱动；它是整个桌面，崩了或卡了就什么都不能用。

5.2 结构

  • shell 本身就是 freedesktop 通知守护进程（notifications.md）。
  • 第三方插件 clone 到 ~/.config/omarchy/plugins/<id>/，没有沙箱，拥有你用户的全部权限（第三方插件）。
  • 空闲时 shell 不能 spawn 进程，由测试 shell-idle-spawn-test.sh 把关。

5.3 菜单：数据驱动

菜单是 omarchy.menu 插件，定义全部在一个 JSONC 文件 omarchy-menu.jsonc 里（约 436 个条目）。规则（menu.md）：

  • key 用点号表示层级：trigger.share.file 是 trigger.share 的子项；有 action 的是动作，否则是子菜单。
  • when / checked / disabled 是 bash 条件，打开菜单时批量放进 8 个并行子 shell 求值，先用上次结果、不等待（Guards）。
  • aliases 是可直接 summon 的短名，快捷键用的就是它们（如 theme → appearance.theme，L89）。
  • 用户的 ~/.config/omarchy/extensions/omarchy-menu.jsonc 按 key 覆盖默认，新 id 追加到末尾（mergeMenuSources）。
类比 · 菜单是一张点菜单，命令是后厨的工位

菜单上每一行只是“名字 + 去哪个工位”：action 里写的就是某个 omarchy-* 命令。快捷键、菜单、CLI 是三个点菜窗口，最后都落到同一个工位上。所以给系统加一个功能，正确的顺序是先在 bin/ 做出工位（命令），再在菜单里加一行、需要的话绑一个快捷键——而不是把逻辑写进菜单或快捷键里。

6. 主题流水线

6.1 职责与难点

职责：omarchy theme set <名字> 之后，桌面边框、shell、四种终端、btop、Neovim、浏览器、GTK、VS Code、Obsidian、Slack，以及 Claude Code / OpenCode / Pi / Hermes 等代理的 TUI 全部换色。难点：二十多个应用接受主题的方式各不相同（重载、信号、文件 watch、策略文件）；切换要原子（不能出现一半新一半旧）；外部下载的主题可能夹带能执行的代码。

6.2 数据：调色板 + 模板

  • 每个主题目录有一个语义调色板 colors.toml（accent、四级背景、四级前景、命名色及 bright_*，例如 tokyo-night），可选 backgrounds/、preview.png、icons.theme、手写的 neovim.lua / vscode.json、shell.<section>.toml 等（theming.md）。内置 23 个主题，其中 3 个浅色。
  • default/themed/ 下 23 个模板，占位符 {{ background }}、{{ accent_rgb }}、{{ mix a b 15% }} 等（占位符），由 render_templates 用一个 awk 进程全部渲染。主题目录里已有同名文件就跳过模板，所以手写文件优先；用户模板 ~/.config/omarchy/themed/*.tpl 先于内置模板处理。

6.3 切换过程

▶ omarchy-theme-set 的五个阶段
1. 组装 staging

加锁（flock，L398–399），清空 next-theme，复制内置主题，再叠加 ~/.config/omarchy/themes/<名字>/。如果用户主题目录里有 .git（即通过 omarchy theme install 装的），会丢弃所有 .lua、终端配置和 vscode.json，名单见 INSTALLED_THEME_DENIED——这些文件都能执行代码。

2. 渲染模板

omarchy-theme-set-templates 先用 omarchy-theme-color --all 解析调色板（含派生色），再把用户模板和内置模板渲染进 staging 目录。

3. 原子替换

mv next-theme theme（L490），再写 theme.name（L501）。读到当前主题的程序永远看到完整的一套。

4. shell 先换

调色板 base64 后经 set_theme_background 用 IPC background themeTransition 交给 shell，壁纸和颜色一起过渡（applyPendingTheme）。

5. 其余应用并行

释放锁后分两组并行：可见层（终端、btop、foot、tmux、Hyprland 重载，L526–534）和其余应用（GNOME、Qt、浏览器、VS Code、Obsidian、Slack、各代理、fcitx5、键盘 RGB，L539–553），最后执行用户 hook theme-set（L601）。

6.4 各应用怎么收到新主题

应用 机制 代码
Hyprland hyprctl reload，重新 require 当前主题的 hyprland.lua restart-hyprctl
Quickshell IPC 推送调色板 Color.qml
Alacritty / Kitty / Ghostty touch 触发 watch / SIGUSR1 / SIGUSR2 restart-terminal
btop SIGUSR2 restart-btop
Chromium 系浏览器 写 root 拥有的 managed policy color.json theme-set-browser
GTK / GNOME gsettings 设 color-scheme 和图标主题 theme-set-gnome

容易误解的地方：终端配置文件第一行只是 import 当前主题生成的文件（如 alacritty.toml L1）。终端的配色由主题管，不要在终端配置里直接改颜色——下次换主题就会被覆盖；要改就改主题或写一个 themed 模板。

7. 更新、迁移与快照

7.1 职责与难点

滚动发行版的更新偶尔会坏；有些修复需要改用户已经存在的文件；更新时 Hyprland 和 shell 都在运行，不能在包替换到一半时重载。

7.2 omarchy update 的时间线

  • 为什么直接 sudo pacman -Syu 会被拒绝：ALPM 钩子 00-omarchy-update-guard.hook 在事务前运行 pacman-guard，只有带 OMARCHY_UPDATE_PACMAN=1（由 omarchy update 设置）或 OMARCHY_ALLOW_DIRECT_PACMAN=1 才放行——绕过会跳过快照和迁移。
  • pacman 跑在 PID 1 的 scope 里（systemd-run --scope，update-pacman），这样 systemd 重新执行自己时不会把更新杀掉。
  • omarchy-settings 升级期间，一对 ALPM 钩子先暂停、后恢复 Hyprland 的自动重载（update-process.md）。

7.3 迁移

  • 格式：migrations/<unix 时间戳>.sh，没有 shebang，以用户身份执行，必须幂等；共 249 个。
  • 运行器 omarchy-migrate 先等 pacman 锁，再按文件名顺序逐个 bash -euo pipefail，成功后在 ~/.local/state/omarchy/migrations/ 留标记（L88–97）。
  • 改用户文件的迁移遵循“只有当你的文件还是出厂原样才替换”：例如 这个迁移 先比较 sha256。
类比 · 装修队只换你没动过的家具

迁移像物业派来的装修队：每次进门前先看一眼清单（~/.local/state/omarchy/migrations/ 里的标记），做过的活不再做；要换家具时先核对它还是不是交房时那一件（比较 sha256），你自己换过的就不碰。所以更新后某个默认改进没生效，往往正是因为你改过那个文件——这时候用 omarchy-refresh-config 拿一份新默认值，再把自己的改动并回去。

  • 登录时只通知、不在后台静默执行（migrate-notify）。

7.4 快照与回滚

snapper 只给根分区配置，只保留 5 个、没有定时快照（snapper/root），每次更新前自动建一个；limine-snapper-sync 让快照出现在启动菜单里。Limine 菜单 1 秒后自动进入（limine.conf），开机时按任意键调出。

注意 · 快照不包括 /home

回滚只恢复系统，不恢复 ~/.config；迁移标记也在家目录里，所以回滚后再更新，已经跑过的迁移不会重跑。改 ~/.config/uwsm/env.d/ 写错导致登录后被踢回登录界面，快照也救不了——要进 TTY 把坏文件移走。

8. “Agentic”：AI 代理是怎么接进系统的

Omarchy 自称“agentic”，在源码里具体是五件事：

  1. 一份给代理读的 skill：SKILL.md 规定 /usr/share/omarchy/ 只读，给出提权规则（有终端用 sudo、没有用 pkexec），教代理用 omarchy commands --json 发现能力、改配置前先备份、改完用 hyprctl configerrors 自检，refresh 前必须征得用户同意。
  2. 装给六家代理：provision-user 把它软链进 ~/.claude/skills、~/.codex/skills、~/.gemini/config/skills、~/.pi/agent/skills、~/.hermes/skills 和通用的 ~/.agents/skills。
  3. 机器可读的 CLI：每个命令的 summary/args/examples 都能用 JSON 导出（第 3 章）。
  4. 代理工具链命令：omarchy-agent（启动默认代理，--local 用本地模型）、多订阅账号切换、统一的 ~/.agents/AGENTS.md、用量面板（约 23 个用量采集器，agent-usage-collectors.md）、本地模型（外部的 omarchy-local-ai 包，local-models.md）。
  5. 主题延伸到代理：Claude Code、Pi、Hermes、T3 Code 都有主题模板（L542–545）。

代理 CLI 本身（claude、codex、opencode 等 23 个）通过 mise 懒安装、每 4 小时自动更新（omarchy-tools.toml）。所以不要用 claude update 这类自带更新器，用 omarchy update。

  6. 常用 SaaS 都做成 Web App 并绑快捷键，带 focus = true 的是单实例。
  7. 说比打快：用听写写 commit message、PR 描述和给代理的 prompt。

10.2 会覆盖你配置的命令

命令 范围 有没有备份
omarchy-refresh-config <文件> 单个文件 有，.bak.<时间戳>，内容没变则删除（L20–39）
Update > Config > Hyprland 7 个 hypr 文件 有
omarchy refresh shell shell.json 有
omarchy-font-set 原地 sed -i 改终端字体行 无（并且会把 Stow 软链变成普通文件）

omarchy reinstall configs 所有种子配置 + Limine + Plymouth 无
omarchy reinstall 包重装 + 回到 stable + 重置配置 无

10.3 维护习惯

  1. 只用 omarchy update，不要直接 pacman -Syu / yay -Syu；保持 stable 通道（它的 Arch 镜像比上游晚一个月，换来的是稳定）。
  2. 更新输出里出现 “boot files did not pass verification” 时不要重启（L149–154）。
  3. 出现 .bak.<时间戳> 文件时 diff 一下，把自己的改动并回去。
  4. 高风险改动（env.d、内核参数、换通道、大量 AUR 包）之前：omarchy-snapshot create，并把 dotfiles commit 一次——快照只有 5 个名额，也不含家目录。
  5. 用 git 管理 ~/.config/hypr/、~/.config/omarchy/、~/.config/uwsm/env.d/、~/.bashrc；不要纳入 ~/.local/state/omarchy/。用 Stow 软链的话，注意 shell.json 和终端配置会被命令原子重写成普通文件，定期 stow --adopt 回收。
  6. 出问题时从轻到重：Update > Hardware 重启单个硬件 → omarchy-restart-shell → 单文件 refresh → 启动菜单选快照回滚 → omarchy-debug 去 Discord 求助 → omarchy reinstall。
要点 · 安全默认值
  • 防火墙拒绝所有入站，只开放 LocalSend 端口；SSH 默认关闭，在 Setup > Security > SSHD 打开并限速（firewall.sh）。
  • sudo 10 分钟超时；连续输错 10 次锁定 2 分钟，TTY 里 faillock --reset 解锁。
  • 免密 sudo 的限时授权就是一个带 NOTAFTER 的 sudoers 文件，开机时被 tmpfiles 清掉（passwordless-sudo.md）。
  • 默认 LUKS 全盘加密（分区代码在外部 ISO 里）。

11. 端到端：按下 Super+Ctrl+T 到全系统换色

挑一条最能串起各组件的路径：用快捷键打开主题选择器，选一个主题。

  1. 绑定：utilities.lua L17 o.bind("SUPER + CTRL + T", "Theme menu", { menu = "theme" })。
  2. command_from 看到 menu，因为 shortcuts 文件登记了 menu theme，shell_dispatcher 生成 hl.dsp.global("omarchy:menu.theme")。
  3. shell 里由 parseShortcuts 注册的 GlobalShortcut 被触发，调用 runShortcut → shell.toggle("omarchy.menu", {menu:"theme"})。
  4. 菜单 resolveRoute 把别名 theme 解析到 appearance.theme（L89），它是一个动作。
  5. summonAction 认出动作是 omarchy-shell shell summon omarchy.image-picker …，于是在进程内打开图片选择器，用户确认后执行 omarchy-theme-set <名字>（applySelected）。CLI 路径 omarchy theme set "Tokyo Night" 从这里汇合：路由器快速路径找到 omarchy-theme-set，名字被规范化成 tokyo-night（L379）。
  6. staging、模板、原子替换（第 6 章）。
  7. shell 经 IPC 收到新调色板，顶栏、菜单、通知立即换色。
  8. 终端、btop、Hyprland 先重载，GNOME、浏览器、VS Code 等随后并行。
  9. 用户的 ~/.config/omarchy/hooks/theme-set* 被执行；可选的跨机器同步（Herdr）默认关闭。

13. 贡献与定制

13.1 开发环境

  • 想改 Omarchy 本身，切到 dev 通道：omarchy-channel-set dev 会把 OMARCHY_PATH 链接到 ~/omarchy 的 git checkout（channel-set），之后 omarchy update 会对它 git pull --ff-only。
  • 测试入口：./test/all（CLI + shell 测试，不含图形验收）、./test/cli、./test/shell；只跑改动相关的文件，并把输出写进日志文件再读（AGENTS.md · Tests）。图形验收测试在一次性 VM 里通过同级的 omarchy-iso 仓库运行（acceptance-tests.md）。
  • 做不同类型的修改前先读 agents/skills/ 下对应的指南：命令元数据、安装脚本、mise 工具、shell 开发、动画、视觉验证、迁移。

13.2 review 规则（摘自 AGENTS.md）

  • 所有命令以 omarchy- 开头，按前缀分组；shebang 必须是 #!/bin/bash；用 [[ ]] 和 (( ))；两空格缩进。
  • 用 helper 而不是裸命令：omarchy-pkg-add / omarchy-pkg-drop、omarchy-notification-send、omarchy-hw-*（不要自己读 uname -m）。
  • 平台缺包或出 bug：先推动上游修，平台专属替代方案是最后手段。
  • 新快捷键按平面规则选键，不挪动已有绑定；新菜单项不加 aliases。
  • 测试必须在不带这次修改时失败；声明式改动（一行菜单、一个配置值）不写测试；迁移不写测试。
  • 有视觉效果的改动必须在运行中的 UI 里验证。
  • commit 要原子化。

13.3 定制路线

方式 代价 依赖
改 ~/.config 几乎为零 理解第 4 章的加载顺序
hook / 菜单扩展 低 hook 用 bash 执行
自建主题、themed 模板 低 第 6 章的占位符语法
shell 插件 中：要写 QML，遵守“空闲不 spawn 进程” omarchy-shell.md、plugins/README.md
dev 通道 / 提 PR 高：系统跑在你的 checkout 上 测试与 review 规则

13.4 仓库里没有的东西

  • 安装器与分区、LUKS 加密：在外部的 omarchy-iso 仓库。
  • 打包脚本：omarchy-pkgs 仓库；pacman 仓库在 pkgs.omarchy.org（pacman-stable.conf）。
  • Apple Silicon 支持：omarchy-mac / omarchy-mac-boot 包，经 lifecycle-dispatch 调用，其他平台对应的操作都是 no-op。
  • 独立程序：Omasnap（截图）、OWE（壁纸引擎）、linux-omarchy 内核、omarchy-nvim（Neovim 配置，本仓库没有 nvim 目录）、omarchy-local-ai、Omawrite / Omacalc / Signed 等小工具。
  • 上游：Hyprland 的 Lua 配置 API、Quickshell。
